# Transforms: contract, compilation, and runtime

This is the single place to look for what a transform is allowed to do, how it gets compiled, and how the backend parses what came out. See `agents/architecture.md` for how transforms fit into the creator/editor product split, and `agents/invariants.md` for the hard rules derived from this doc.

## The contract (`backend/transform-sdk`)

- The author implements `transform_sdk::Transform` for a `Default` struct:
  ```rust
  fn process(&mut self, samples: &[&[f32]], params: &Params<'_>) -> Vec<f32>;
  fn metadata() -> TransformMetadata;
  ```
  `samples` has exactly one entry per declared `Direction::Input` port, in declared order — a single-input transform (the entire pre-multi-input-ports catalog) gets a slice of length 1 and reads `samples[0]`, unchanged in spirit from before. `process` returns this quantum's output — always exactly one array, matching the "exactly one output port" rule `metadata_introspector.rs` enforces — replacing the old in-place `&mut [f32]` mutation. `params` is a `Params<'_>` wrapper (see "Named param access" below), not a bare `&[f32]`, though `params[0]`-style indexing still compiles unchanged. `metadata()` is a static description, called once per compile by the backend's introspection, plus lazily once more on the wasm side itself (see `export_transform!` below) — never per-quantum either way.
- The author calls `transform_sdk::export_transform!(MyType)` exactly once. The macro generates the entire wasm32-unknown-unknown surface — the author never hand-writes `extern "C"` code:
  - `alloc(len) -> *mut f32` — a 1 MiB bump-and-wrap arena, not a real allocator. It never frees. Per quantum, N input buffers + one params buffer + one output buffer are the pointers live at once (not "at most two," pre-multi-input-ports) — still small and fixed relative to the arena at realistic port counts, and each pointer is fully consumed synchronously before the next `alloc`. A transform must not stash a pointer across calls.
  - `process(samples_ptr, num_inputs, block_len, params_ptr, params_len) -> *const f32` — the extern-C entry point. Reads `num_inputs` contiguous buffers of `block_len` floats each (one per declared input port, in declared order) starting at `samples_ptr`, calls the author's `Transform::process`, and returns an arena-allocated pointer to exactly `block_len` result floats (padded/truncated if the author's `process` returned a different length than `block_len`). No separate length query — the caller already knows `block_len`.
  - `transform_metadata_ptr()` / `transform_metadata_len()` — expose a JSON serialization of `Transform::metadata()` for the backend's post-compile introspection. `metadata()` must be stable for a given build. Computed once (`once_cell::Lazy`) and reused for both this JSON export and `Params`'s named-lookup table — whichever caller reaches it first (usually the backend's introspection during compile; on the wasm side itself, lazily, on the module's first `process` call, since the editor worklet never calls `transform_metadata_ptr` — published ports/params come from the DB, not a live wasm call).
  - `transform_abi_version() -> u32` — feature detection, constant `TRANSFORM_ABI_VERSION = 2`. Its *presence* tells a caller the module speaks this array-shaped ABI; its *absence* means a module built against a pre-multi-input-ports SDK, still speaking the old in-place single-buffer `process(ptr, len, params_ptr, params_len)` (no return value). The worklet-side dispatch on this is `graph-worklet.js`'s responsibility (editor-agent) — this SDK only exports it correctly.
  - `memory` is exported automatically via `crate-type = ["cdylib"]`.
- **`PortMetadata` carries a `kind` and `cardinality` alongside `name`/`direction`/`order`/`description`:**
  ```rust
  pub enum PortKind { Program, Sidechain }
  pub enum PortCardinality { Single, Many }
  ```
  `Program` = main signal; unwired **fails closed** — rejected before `process()` ever runs, at the graph-pipeline validation layer (editor-agent's `validateRuntimeGraph.ts`, not this SDK). `Sidechain` = control/detector signal (e.g. a compressor's key input); unwired always resolves to a silence buffer, never an error — a routing-layer behavior, not something this SDK implements, but the enum's doc comments must stay accurate about it. `Single` = exactly one edge may target the port; `Many` is an explicit opt-in for the narrow legitimate summing case (multiple sources landing on one "mix"-style port) — no longer the implicit whole-node default every port got before this port model existed. Output ports must be `Program`/`Single` — `metadata_introspector.rs` rejects anything else, and rejects any module declaring other than exactly one output port.
- **Named param access** (additive, no wire-format change): `Params<'a>` wraps the raw positional `&[f32]` with the names already declared in `metadata().params`. `Index<usize, Output = f32>` keeps `params[0]`-style call sites compiling unchanged; `.named("threshold") -> Option<f32>` is pure upside on top. `graph-worklet.js`'s `callWasm` still hands a flat positional `Float32Array` — nothing changes at the ABI boundary for params.
- The module must declare **zero imports**. Both the editor's worklet and the backend's introspection step instantiate it with no host imports at all, and both will refuse to run a module that declares any.
- The whole transform definition — `name`, `description`, ports, and params — is entirely code-first: the author declares all of it literally in `metadata()` (see the `DEFAULT_CODE` template in `frontend/src/components/creator/code-editor.tsx` for the exact shape). Nothing infers any of this from function signatures or static analysis, and `metadata()` must stay in sync with what `process()` actually reads/writes — the SDK cannot enforce that.

## What's allowed in the editor at runtime

- `frontend/src/audio/worklet/graph-worklet.js` is the only runtime caller of a transform's wasm exports, on the dedicated `AudioWorkletProcessor` thread.
- Block size is fixed at `BLOCK_SIZE = 128` samples per quantum.
- **As of the multi-input named ports ABI (`transform_abi_version = 2`), `callWasm`'s two-buffer in-place pattern (allocate input + params, call `process`, read the mutated input buffer back) is superseded by the array-shaped, return-value-based `process(samples_ptr, num_inputs, block_len, params_ptr, params_len) -> result_ptr` described above.** Wiring the worklet's per-port routing and ABI-version dispatch (legacy in-place vs. new array-shaped) is `editor-agent`'s work, sequenced after this SDK/introspection/migration slice — see `agents/decisions/0004-multi-input-named-ports.md`. Until that lands, this line is aspirational for already-published legacy binaries and load-bearing for any transform newly compiled against the current SDK.
- `WebAssembly.instantiate(binary)` is called with **no import object**. A transform that declares any import fails to instantiate in the browser; this is intentionally mirrored server-side (below), so a module that passes backend introspection is guaranteed loadable in the editor too.
- The editor never compiles transforms. It only fetches and caches already-published binaries (`apiGetTransformBinary`/`apiGetTransformBinaries`) and hands them to the worklet via the `SET_GRAPH` message.

## Three buckets: compile, save, publish

A transform's in-progress state is split into three independent storage locations, each owned by exactly one action. None of them infer or trigger another — moving from one to the next always requires an explicit user action.

| Bucket | Table(s) | Written by | Meaning |
|---|---|---|---|
| 1. Compile (check) | `transform_ticket` + `transform_resource` | a successful/failed compile ticket, always | "this specific compile attempt produced this artifact" — immutable history, many rows accumulate, never live |
| 2. Save | `transform_draft` (one row per transform) | the Save action | the creator's current state: source text always, plus a binary/metadata snapshot *if* a compiled resource was attached at save time |
| 3. Publish | `transform_binary` + `transform.{name,description}` + `transform_port`/`transform_param` | the Publish action | the live artifact — what the editor surface actually fetches and runs |

None of these tables reference each other except by explicit action: a ticket's resource never becomes live on its own, and a save never gets published on its own. This is a deliberate rejection of the earlier "v1 auto-publish-on-success" behavior — it was replaced because a compile ticket succeeding is not the same claim as "the creator wants this live now."

### Bucket 1 — Compile

1. Creator submits `{transform_id, source_code}` (`POST /transforms/tickets`, handled by `backend/api/src/tickets/`) → a `DbTicket` is created in state `Processing`.
2. A worker (`backend/api/src/ticket_worker/worker.rs`) consumes a `TicketCreatedEvent` and runs `Processor::process` (`backend/api/src/ticket_worker/processor/processor.rs`):
   1. confirm the ticket exists;
   2. `build_job::compile_transform_source` writes the user's source **byte-for-byte** (no wrapping, so compiler error line numbers match what the user wrote) as `src/lib.rs` into a per-job scratch dir, generates an entirely backend-authored `Cargo.toml` pinned to the local `transform-sdk` path, and runs `cargo build --release --target wasm32-unknown-unknown --offline` as a subprocess with a timeout and output-size cap;
   3. `metadata_introspector::introspect_metadata` instantiates the resulting wasm with wasmtime, zero host imports, and a fuel budget — this briefly executes attacker-controlled code server-side — then reads back name/description/ports/params as JSON;
   4. validates the parsed metadata (name non-empty, port names non-empty, param names/orders unique);
   5. **stores the full artifact** (wasm bytecode + name + description + ports + params) into `transform_resource` via `create_resource` — this is the *only* write a compile ticket makes; it never touches `transform_draft` or the live tables;
   6. the ticket flips to `Successful{resource_id}`. Any failure at steps 2–4 instead flips it to `Failed{message}`.
3. The creator frontend polls ticket status (`useCompileTicketStatus`) until terminal, then fetches the successful compile resource. That resource response carries a paired `{source_code, wasm_base64}` package: the source is read from the ticket that produced the resource, so the browser never combines arbitrary current editor text with bytes from another compile.
4. **Try it and temporary Save handoff:** the Creator keeps this source/WASM package in non-persisted `CreatorStore` state. It can run the bytes through the same worklet module and message protocol the editor uses (`graph-worklet.js` / `WorkletMessageSender`, **not** `WorkletController`), wrapped in a degenerate one-node `CompiledGraph` via a creator-scoped wrapper (`frontend/src/components/creator/creatorTransformPreview.ts`). It also sends the package back only if its source still exactly equals the editor buffer. A refresh before Save loses the in-memory package and requires a new retrieval/compile.

### Bucket 2 — Save

- `PUT /draft_transforms/{id}/save-primitive` (`useSaveTransform`, wired into the code editor's Save button) always overwrites `transform_draft.source_code`. This is a plain sync overwrite — never blocked by, or dependent on, compiling.
- It optionally takes `wasm_base64` alongside `source_code`. If supplied, Save decodes it, enforces the configured WASM-byte limit, re-runs fuel-limited/zero-import metadata introspection, and atomically writes its binary, derived metadata, and `wasm_source_code` snapshot to `transform_draft`. It does not read ticket/resource state. If omitted, any previously saved binary/metadata is left untouched — a source-only save never wipes out the last good build.
- The Creator's `attachableCompiledDraft` guard (`code-editor.tsx`) only sends a source/WASM package while the editor buffer still equals that package's ticket source. Edit anything after compiling and Save reverts to source-only until another successful package is fetched. This is a frontend consistency guard only: without a signed receipt or a backend resource lookup, Save cannot prove the supplied WASM was compiled from the supplied source. See decision 0009.
- **Composites save unconditionally, with no validation.** `PUT /transforms/{id}/save-composite` (`useSaveCompositeTransform`) always overwrites `transform_draft.graph_definition` as-is — it does **not** run `composite_validator::validate_composite_graph` and does **not** write `transform_draft.ports` (whatever `ports` already held — empty for a brand-new draft, or the last successfully-derived set — is left untouched). This lets a creator drag in nodes and wire them up incrementally without the graph having to be structurally complete at every intermediate save. It unconditionally flips `transform_draft.is_validated` back to `false` alongside the `graph_definition` write — see the composite draft validation sub-state below. See `agents/decisions/0007-composite-draft-validation-gate.md`.

### Composite draft validation — a fourth, independent sub-state between Save and Publish

- Composites have their own bucket-2-adjacent sub-state that primitives don't need (Compile already plays this role for them, see bucket 1): `transform_draft.is_validated`, a boolean written only by `POST /transforms/{id}/validate` (`useValidateCompositeTransform` / `TransformsProvider::validate_composite_draft`).
- **Validate runs the exact `composite_validator::validate_composite_graph` check Save used to run before this change**, against the *currently-persisted* `transform_draft.graph_definition` (not any uncommitted canvas edits — those must be Saved first). On success it writes the derived `ports` (same derivation as before) and sets `is_validated = true`. On failure it leaves `ports`/`is_validated` untouched and returns the same validation error shape Save's old rejection used to produce, for the composite canvas's Validate button to surface.
- **Staleness.** Any subsequent `save_composite_draft` write unconditionally resets `is_validated` to `false` — any graph edit invalidates the last validate result until Validate is explicitly re-run. This is the same "stale until re-verified" idea as `attachableResourceId` in the primitive code editor (`code-editor.tsx`), just backend-owned and persisted instead of frontend-derived from a source-text comparison.
- **Gates Publish, then Publish still re-validates from scratch.** As of `agents/decisions/0008-publish-requires-validated-composite-draft.md` (superseding item 4 of 0007), Publish's composite branch (below) first checks `is_validated == true` and fails fast with a distinct validation error if not — a creator can no longer publish without having clicked Validate on the currently-persisted graph. This is *not* a replacement for the from-scratch re-validation Publish already ran: once the gate passes, Publish still independently re-runs `validate_composite_graph`, because a leaf transform may have been unpublished or deleted since the last Save/Validate. The two checks are additive, not alternatives.
- **A live consumer now reads it.** Unlike at 0007's time, `is_validated` is no longer purely defensive plumbing — `publish_transform` reads it as a precondition. It's still returned wherever `transform_draft`/`DbTransformDraft`/`DbTransformDefinition` already flow (including `TransformDefinitionDto`), which was shaped this way in 0007 specifically so a consumer could read it without a schema/API rework — this is that consumer. See `agents/decisions/0008-publish-requires-validated-composite-draft.md`.

### Bucket 3 — Publish

- `POST /transforms/{id}/publish` (`usePublishTransform`) reads `transform_draft` and, if it has a binary, calls the existing `publish_compiled_transform` to atomically write wasm bytecode + source + name + description + ports + params into the live tables. **It does not compile anything** — it bundles what's already been saved. If bucket 2 has no binary yet (never saved with a successful build), it fails with a validation error.
- This is intentionally the only place `publish_compiled_transform` is called from now — the ticket worker no longer calls it.
- **Composite publish gates on `is_validated`, then independently re-validates from scratch anyway.** `publish_transform`'s composite branch (`transforms_provider_service.rs`) first checks `transform_draft.is_validated == true` and fails fast with a distinct validation error ("composite draft must be validated before publishing") if the currently-persisted graph hasn't passed Validate — see `agents/decisions/0008-publish-requires-validated-composite-draft.md`, superseding item 4 of `agents/decisions/0007-composite-draft-validation-gate.md`. Once that gate passes, it still reads `transform_draft.graph_definition` and re-runs `composite_validator::validate_composite_graph` itself, exactly as Validate does — a leaf transform referenced by the graph may have been unpublished or deleted since the last save or the last Validate, so the gate does not make the re-validation redundant. On success it writes the freshly re-derived ports directly into `transform_composite`/`transform_port`, independent of whatever `transform_draft.ports` currently holds (only `is_validated` itself is now a precondition, not the stale `ports` snapshot).
- **Publish requires the saved binary and saved source to correspond.** A source-only save (no `wasm_base64`) leaves a previously-attached binary in place without updating it. `publish_transform` (`transforms_provider_service.rs`) checks `transform_draft.wasm_source_code == transform_draft.source_code` before calling `publish_compiled_transform`; a mismatch fails with a validation error telling the creator to recompile and save the matching package.
- **Republish overwrites in place, with no version pin.** Hitting Publish on an already-published transform re-runs the same atomic write — no versioning, no *blocking* compatibility check against existing editor graphs (which reference a transform by bare ID with no version pin in `graph_state`). This is an accepted risk, not an oversight — see `agents/decisions/0002-transform-draft-lifecycle-decisions.md`.
- **Advisory republish port-shape warning.** `GET /transforms/{id}/publish/port-diff` (`TransformsProvider::diff_publish_port_shape`) diffs the port shape about to be published (bucket 2, `transform_draft.ports`) against what's currently live (bucket 3, `transform_port`) — count/kind/cardinality per port, ignoring name (a pure rename doesn't trip it), and always reports no change for a transform's first-ever publish. It never blocks or gates `publish_transform` itself — purely advisory, polled by the creator frontend (`code-editor.tsx`'s publish handler) immediately before calling Publish, to show a non-blocking confirm dialog when the shape changed. See `agents/decisions/0004-multi-input-named-ports.md`.

### Draft deletion

- `DELETE /transforms/{id}` (`apiDeleteTransform`, wired to a per-row delete button in `transforms-sidebar.tsx` via `useDeleteTransform`/`TransformController.handleDeleteTransform`) only succeeds for a transform that has never been published (no row ever written to `transform_binary`) — `PostgresTransformsDataProvider::delete_transform` checks `transform_binary` first and returns a `Conflict` (surfaced as HTTP 409) otherwise. On success it cascades to `transform_draft`, `transform_ticket` (and transitively `transform_resource`), `transform_port`, and `transform_param` via the `ON DELETE CASCADE` FKs already in place from migrations 0004/0009/0011/0014 — no new migration was needed for the cascade itself, only for the unrelated `wasm_source_code` column above.

## What this means for other surfaces

- The creator's transform properties panel (`frontend/src/components/creator/transform-properties-panel.tsx`) is fully read-only — name, description, ports, and params only change via Publish (bucket 3), never hand-edited.
- Any change to the ABI (macro-generated exports, arena semantics, block size, import policy) must be reflected in all three of: `backend/transform-sdk`, `metadata_introspector.rs`'s validation, and `graph-worklet.js` — they currently agree by convention, not by shared code.
