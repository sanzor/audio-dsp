# Transforms: contract, compilation, and runtime

This is the single place to look for what a transform is allowed to do, how it gets compiled, and how the backend parses what came out. See `agents/architecture.md` for how transforms fit into the creator/editor product split, and `agents/invariants.md` for the hard rules derived from this doc.

## The contract (`backend/transform-sdk`)

- The author implements `transform_sdk::Transform` for a `Default` struct:
  ```rust
  fn process(&mut self, samples: &[&[f32]], params: &Params<'_>) -> Vec<f32>;
  fn metadata() -> TransformMetadata;
  ```
  `samples` has exactly one entry per declared `Direction::Input` port, in declared order — a single-input transform (the entire pre-multi-input-ports catalog) gets a slice of length 1 and reads `samples[0]`, unchanged in spirit from before. `process` returns this quantum's output — always exactly one array, matching the "exactly one output port" rule `metadata_introspector.rs` enforces — replacing the old in-place `&mut [f32]` mutation. `params` is a `Params<'_>` wrapper (see "Named param access" below), not a bare `&[f32]`, though `params[0]`-style indexing still compiles unchanged. `metadata()` is a static description, called once per compile by the backend's introspection, plus lazily once more on the wasm side itself (see `export_transform!` below) — never per-quantum either way.
- The author calls `transform_sdk::export_transform!(MyType)` exactly once. The macro generates the entire wasm32-unknown-unknown surface — the author never hand-writes `extern "C"` code:
  - `alloc(len) -> *mut f32` — a 1 MiB bump-and-wrap arena, not a real allocator. It never frees. Per quantum, N input buffers + one params buffer + one output buffer are the pointers live at once (not "at most two," pre-multi-input-ports) — still small and fixed relative to the arena at realistic port counts, and each pointer is fully consumed synchronously before the next `alloc`. A transform must not stash a pointer across calls.
  - `process(samples_ptr, num_inputs, block_len, params_ptr, params_len) -> *const f32` — the extern-C entry point. Reads `num_inputs` contiguous buffers of `block_len` floats each (one per declared input port, in declared order) starting at `samples_ptr`, calls the author's `Transform::process`, and returns an arena-allocated pointer to exactly `block_len` result floats (padded/truncated if the author's `process` returned a different length than `block_len`). No separate length query — the caller already knows `block_len`.
  - `transform_metadata_ptr()` / `transform_metadata_len()` — expose a JSON serialization of `Transform::metadata()` for the backend's post-compile introspection. `metadata()` must be stable for a given build. Computed once (`once_cell::Lazy`) and reused for both this JSON export and `Params`'s named-lookup table — whichever caller reaches it first (usually the backend's introspection during compile; on the wasm side itself, lazily, on the module's first `process` call, since the editor worklet never calls `transform_metadata_ptr` — published ports/params come from the DB, not a live wasm call).
  - `transform_abi_version() -> u32` — feature detection, constant `TRANSFORM_ABI_VERSION = 2`. Its *presence* tells a caller the module speaks this array-shaped ABI; its *absence* means a module built against a pre-multi-input-ports SDK, still speaking the old in-place single-buffer `process(ptr, len, params_ptr, params_len)` (no return value). The worklet-side dispatch on this is `graph-worklet.js`'s responsibility (editor-agent) — this SDK only exports it correctly.
  - `memory` is exported automatically via `crate-type = ["cdylib"]`.
- **`PortMetadata` carries a `kind` and `cardinality` alongside `name`/`direction`/`order`/`description`:**
  ```rust
  pub enum PortKind { Program, Sidechain }
  pub enum PortCardinality { Single, Many }
  ```
  `Program` = main signal; unwired **fails closed** — rejected before `process()` ever runs, at the graph-pipeline validation layer (editor-agent's `validateRuntimeGraph.ts`, not this SDK). `Sidechain` = control/detector signal (e.g. a compressor's key input); unwired always resolves to a silence buffer, never an error — a routing-layer behavior, not something this SDK implements, but the enum's doc comments must stay accurate about it. `Single` = exactly one edge may target the port; `Many` is an explicit opt-in for the narrow legitimate summing case (multiple sources landing on one "mix"-style port) — no longer the implicit whole-node default every port got before this port model existed. Output ports must be `Program`/`Single` — `metadata_introspector.rs` rejects anything else, and rejects any module declaring other than exactly one output port.
- **Named param access** (additive, no wire-format change): `Params<'a>` wraps the raw positional `&[f32]` with the names already declared in `metadata().params`. `Index<usize, Output = f32>` keeps `params[0]`-style call sites compiling unchanged; `.named("threshold") -> Option<f32>` is pure upside on top. `graph-worklet.js`'s `callWasm` still hands a flat positional `Float32Array` — nothing changes at the ABI boundary for params.
- The module must declare **zero imports**. Both the editor's worklet and the backend's introspection step instantiate it with no host imports at all, and both will refuse to run a module that declares any.
- The whole transform definition — `name`, `description`, ports, and params — is entirely code-first: the author declares all of it literally in `metadata()` (see the `DEFAULT_CODE` template in `frontend/src/components/creator/code-editor.tsx` for the exact shape). Nothing infers any of this from function signatures or static analysis, and `metadata()` must stay in sync with what `process()` actually reads/writes — the SDK cannot enforce that. **Exception, as of `agents/decisions/0012-draft-name-description-editable.md`:** `metadata()` still supplies a draft's *initial* name/description at creation time, and is still what compile/introspection/validation reads and reports — but it is no longer the ongoing single source of truth for a draft's *displayed* name/description once the user starts editing them. Editing happens via optional `name`/`description` fields on `PUT /draft_transforms/{id}/save`'s payload (both the primitive and composite variants) — not a separate endpoint. Omitted/`None` leaves the existing value untouched; a supplied value takes priority over both the existing value and (for a primitive) the just-compiled metadata's name/description, which is only ever a last-resort seed. Publish is unaffected — it still copies forward whatever is currently persisted on `transform_draft` into the published `transform` row.

## What's allowed in the editor at runtime

- `frontend/src/audio/worklet/graph-worklet.js` is the only runtime caller of a transform's wasm exports, on the dedicated `AudioWorkletProcessor` thread.
- Block size is fixed at `BLOCK_SIZE = 128` samples per quantum.
- **As of the multi-input named ports ABI (`transform_abi_version = 2`), `callWasm`'s two-buffer in-place pattern (allocate input + params, call `process`, read the mutated input buffer back) is superseded by the array-shaped, return-value-based `process(samples_ptr, num_inputs, block_len, params_ptr, params_len) -> result_ptr` described above.** Wiring the worklet's per-port routing and ABI-version dispatch (legacy in-place vs. new array-shaped) is `editor-agent`'s work, sequenced after this SDK/introspection/migration slice — see `agents/decisions/0004-multi-input-named-ports.md`. Until that lands, this line is aspirational for already-published legacy binaries and load-bearing for any transform newly compiled against the current SDK.
- `WebAssembly.instantiate(binary)` is called with **no import object**. A transform that declares any import fails to instantiate in the browser; this is intentionally mirrored server-side (below), so a module that passes backend introspection is guaranteed loadable in the editor too.
- The editor never compiles transforms. It only fetches and caches already-published binaries (`apiGetTransformBinary`/`apiGetTransformBinaries`) and hands them to the worklet via the `SET_GRAPH` message.

## Three buckets: compile+save, publish

A transform's in-progress state used to be split into three buckets — an
async Compile ticket, Save, and Publish. As of
`agents/decisions/0010-remove-ticket-based-compile.md`, Compile is no
longer a separate stage: it runs synchronously inside Save. Two buckets
remain, each owned by exactly one action, and neither infers or triggers
the other:

| Bucket | Table(s) | Written by | Meaning |
|---|---|---|---|
| 2. Save (compiles inline) | `transform_draft` (one row per transform) | the Save action | the creator's current state: source text plus its binary/metadata snapshot — always both together, or neither |
| 3. Publish | `transform_binary` + `transform.{name,description}` + `transform_port`/`transform_param` | the Publish action | the live artifact — what the editor surface actually fetches and runs |

A save never gets published on its own — this is a deliberate rejection of the earlier "v1 auto-publish-on-success" behavior, and remains true post-0010: a successful Save is not the same claim as "the creator wants this live now."

### Bucket 2 — Save (primitive: compiles inline)

As of `agents/decisions/0011-transform-draft-api-reshape.md`, both draft
kinds save through one unified route:
`PUT /draft_transforms/{id}/save` (`useSaveTransform`/`useSaveCompositeTransform`,
wired into the code editor's and composite canvas's Save buttons), body
`SaveDraftParams` (an untagged enum — the draft's persisted `kind` picks
the variant, so the body never needs to name it):

- **Primitive** — `{source_code}` only. `TransformDraftsProviderService::save_primitive_draft`
  (`backend/api/src/transform_drafts/transform_drafts_provider_service.rs`)
  runs the full compile+introspect pipeline synchronously, inline in the
  request, before writing anything:
  1. `build_job::compile_transform_source` (`backend/api/src/transform_drafts/processor/build_job.rs`) writes the user's source **byte-for-byte** (no wrapping, so compiler error line numbers match what the user wrote) as `src/lib.rs` into a per-job scratch dir, generates an entirely backend-authored `Cargo.toml` pinned to the local `transform-sdk` path, and runs `cargo build --release --target wasm32-unknown-unknown --offline` as a subprocess with a timeout and output-size cap;
  2. `wasm_parser::parse_wasm` (`backend/api/src/transform_drafts/processor/wasm/wasm_parser.rs`) instantiates the resulting wasm with wasmtime, zero host imports, and a fuel budget — this briefly executes attacker-controlled code server-side — then reads back name/description/ports/params as JSON;
  3. `validator::validate_primitive` (`backend/api/src/transform_drafts/processor/validator/validator.rs`) validates the parsed metadata (name non-empty, port names non-empty, param names/orders unique, exactly one `Program`/`Single` output port);
  4. on success, `save_primitive_draft` atomically overwrites `transform_draft`'s `source_code`, `wasm_bytecode`, `wasm_source_code`, `name`, `description`, and `metadata` together.
  A failed compile or failed validation rejects the whole save — nothing is persisted, `source_code` included. There is no source-only save anymore: a saved draft's source and binary always correspond, by construction, so Publish's old "does the saved binary match the saved source" staleness check can never actually fire post-0010 (kept as a defensive check regardless — see Bucket 3 below).
- **Composite** — `{graph_definition}`. Saves unconditionally, with no validation: it does **not** run `composite_validator::validate_composite_graph` and does **not** derive/write ports. This lets a creator drag in nodes and wire them up incrementally without the graph having to be structurally complete at every intermediate save. Validation is a fully separate, standalone action (below) — there is no persisted "is this graph currently valid" flag anymore (see the removed sub-state below).
- `POST /draft_transforms/{id}/validate-source` (`useValidateTransformSourceCode`, the code editor's "Check" button) is a standalone, fast compile-only check — doesn't save, doesn't persist anything, just returns 200 clean or 400 with the compiler diagnostics the same rejected-Save path would have produced.
- `GET /draft_transforms/{id}/binary` returns the binary already attached by a successful primitive Save, for Creator's local Try It worklet. It is owner-only and read-only: it never compiles, saves, or publishes. The frontend must Save again before previewing changed source.

### Composite graph validation — standalone, not persisted (removed: `is_validated`)

`transform_draft.is_validated` — introduced by `agents/decisions/0007-composite-draft-validation-gate.md`
and made a Publish precondition by `agents/decisions/0008-publish-requires-validated-composite-draft.md`
— **has been removed entirely from the Rust backend** (0011 supersedes both
0007 and 0008; the migration 0022 DB column is left in place but nothing
reads or writes it). In its place:

- `POST /draft_transforms/{id}/validate-graph`, body `{graph_json: string}` — a JSON-stringified graph, which **may include unsaved canvas edits** (unlike the old model, which only ever checked the last-persisted graph). Runs the same `composite_validator::validate_composite_graph` check Save used to run pre-0010, against whatever graph the caller hands it. Returns `{ports: PortMetadataJson[]}` on success (`order`, not `port_order`; no `port_id` — derived on the fly, never persisted) and the validation error shape on failure. **Persists nothing, gates nothing** — the composite canvas's Validate button surfaces the result transiently (a toast/inline panel), and it's the caller's job to decide when to call it (typically before Save or before Publish, as a sanity check), not something the backend enforces a sequence around.
- Publish's composite branch (below) no longer gates on any persisted flag — it always independently runs `validate_composite_graph` against the currently-saved graph before publishing, exactly as before, just without the pre-check gate in front of it.

### Bucket 3 — Publish

- Publish is split by kind into two routes — `POST /draft_transforms/{id}/publish-primitive` and `POST /draft_transforms/{id}/publish-composite` (`usePublishPrimitiveTransform`/`usePublishCompositeTransform`) — both calling the same underlying `publish(id)`, just with kind-specific 400 messages instead of one route branching internally. `publish(id)` reads `transform_draft` and, if it has a binary, calls the existing `publish_compiled_transform` to atomically write wasm bytecode + source + name + description + ports + params into the live tables. **It does not compile anything** — it bundles what's already been saved. If bucket 2 has no binary yet (never saved successfully), it fails with a validation error.
- This is intentionally the only place `publish_compiled_transform` is called from — there is no ticket worker anymore (`agents/decisions/0010-remove-ticket-based-compile.md`).
- **Composite publish re-validates from scratch — no persisted gate anymore.** `publish_transform`'s composite branch (`transforms_provider_service.rs`) reads `transform_draft.graph_definition` and runs `composite_validator::validate_composite_graph` itself before publishing — a leaf transform referenced by the graph may have been unpublished or deleted since the last save, so this can't be skipped. On success it writes the freshly re-derived ports directly into `transform_composite`/`transform_port`. (Pre-0011, this was gated by `is_validated == true` first, per 0008 — that gate is gone; the re-validation itself is unchanged.)
- **Publish still checks the saved binary and saved source correspond.** Since 0010, a saved primitive draft's source and binary always match by construction (Save rejects outright rather than ever leaving them out of sync), so this check is now defensive rather than load-bearing — kept because a future change to Save's guarantee shouldn't silently reopen this hole. `publish_transform` (`transforms_provider_service.rs`) checks `transform_draft.wasm_source_code == transform_draft.source_code` before calling `publish_compiled_transform`; a mismatch fails with a validation error telling the creator to recompile and save again.
- **Republish overwrites in place, with no version pin.** Hitting Publish on an already-published transform re-runs the same atomic write — no versioning, no *blocking* compatibility check against existing editor graphs (which reference a transform by bare ID with no version pin in `graph_state`). This is an accepted risk, not an oversight — see `agents/decisions/0002-transform-draft-lifecycle-decisions.md`.
- **Advisory republish port-shape warning: removed, not replaced.** The old `GET /transforms/{id}/publish/port-diff` advisory check (`agents/decisions/0004-multi-input-named-ports.md`) doesn't exist on either controller post-reshape and was never rebuilt — `agents/decisions/0011-transform-draft-api-reshape.md` removed the dead frontend call site. A route to warn before a republish changes port shape would need to be added fresh to `draft_transforms_controller.rs` if still wanted.

### Draft deletion

- `DELETE /draft_transforms/{id}` (`apiDeleteTransform`, wired to a per-row delete button in `transforms-sidebar.tsx` via `useDeleteTransform`/`TransformController.handleDeleteTransform`) only succeeds for a transform that has never been published (no non-empty `wasm_bytecode` on the shared `transform` row) — `delete_transform_draft` checks that first and returns a `Conflict` (surfaced as HTTP 409) otherwise. On success it cascades via the existing `ON DELETE CASCADE` FKs. (`transforms_controller.rs` also exposes `DELETE /transforms/{id}` with the identical guard/cascade, kept in sync by hand as its own SQL rather than a shared call — see `TransformDraftId`'s doc comment for why a draft and its published transform share one underlying row id. The Creator frontend calls the `/draft_transforms/{id}` one, matching what this call site has always semantically meant.)

## What this means for other surfaces

- The creator's transform properties panel (`frontend/src/components/creator/transform-properties-panel.tsx`) is mostly read-only, with one exception: **name and description are editable per-draft**, as optional fields folded into Save (`name`/`description` on `SavePrimitiveParams`/`SaveCompositeParams`) rather than a separate endpoint — guarded client- and server-side against a blank name. Editing the input/textarea only updates `CreatorStore`'s `editingTransformMetadata` buffer; blur/Enter just runs the client-side blank-name check. The edit actually persists the next time Save Draft is clicked (`code-editor.tsx` for primitive, `composite/composite-canvas.tsx` for composite, `unsaved-creator-changes-modal.tsx` when a pending switch flushes it), which reads that same buffer and includes `name`/`description` in its Save payload only when `isMetadataDirty` — an unrelated source-only/graph-only save omits the keys rather than uselessly re-sending unchanged values. Because a metadata edit no longer persists independently on blur, `CreatorStore.requestSelectTransform`/`requestCreateTransform` also gate on `isMetadataDirty` (alongside the pre-existing source/composite-graph dirty checks) so switching transforms with an unsaved rename pending routes through the unsaved-changes modal instead of silently discarding it. There is no backend sync of any kind into `transform` from this — the left transforms-sidebar (`transforms-sidebar.tsx`) independently resolves each listed transform's draft (`POST /draft_transforms/resolve`, `useTransformDraftStore`) and merges the draft's name/description over the bucket-3 (`useListTransforms`/`useTransformStore`) values for display, client-side — this is what keeps the sidebar from going stale after a rename, not a backend column-sync; the consolidated Save mutation invalidates the same query keys a rename needs refreshed. Ports and params are unaffected by this — they remain fully read-only in this panel, sourced from bucket-3 (`useGetTransformDefinition`), and only ever change via Publish. See `agents/decisions/0012-draft-name-description-editable.md`.
- Any change to the ABI (macro-generated exports, arena semantics, block size, import policy) must be reflected in all three of: `backend/transform-sdk`, `wasm_parser.rs`/`validator.rs`'s validation, and `graph-worklet.js` — they currently agree by convention, not by shared code.
- **No HTTP response, on either controller, carries a real persisted port/param id anymore.** `TransformDraftDto`/`TransformDto` only carry `metadata_json` (a JSON string); parsing it (`Services/TransformService.ts`'s `parseTransformMetadata`) yields `PortMetadataJson`/`ParamMetadataJson` with no id field at all (derived at compile/validate time, never persisted with one). The frontend's `TransformPort`/`TransformParam` domain types still declare `port_id`/`param_id` (unchanged, since `editor-agent`'s `GraphCompiler.ts` and friends depend on that shape) — `parseTransformMetadata` synthesizes them as a stable-per-response array index. See `agents/decisions/0011-transform-draft-api-reshape.md`'s consequences section for the open question this leaves for `editor-agent`/`product-owner`.
